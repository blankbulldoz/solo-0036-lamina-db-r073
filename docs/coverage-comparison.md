# 精简与较完整教学材料的对照：能排除什么，代价是什么

本文对照两档材料——核心篇（`docs/query-semantics-guide.md`，42 条检查）与扩展篇（`docs/query-semantics-extended.md`，30 条检查）——回答一个问题：**各自能排除哪些错误假设，为此付出什么代价**。

方法：把每个案例当作一个*判别实验*。一个案例有价值，当且仅当存在某个自洽但错误的解释，它预测的结果与正确规则不同，而案例能把两者分开。少量案例常常让错误解释碰巧正确（错误规则与正确规则在该输入上输出相同）；展开所有交错又会失去可读性。两档材料是这个权衡上的两个点。

## 错误假设排除清单

### 核心篇可排除（17 条）

| 错误假设 | 判别案例 |
| --- | --- |

| 降序时 null 在前 | B2 |
| 同值并列时主键随排序方向翻转 | B2 |
| put 是字段级合并（缺失列保留旧值） | C1 |
| 暂存写对其他观察者可见 | C2、C3 |
| 提交后已开始的事务也看到新值 | C5 |
| SQL 入口不能选择事务/at 快照 | C6-sql、C7-sql |
| sum 溢出回绕为负数 | D1 |
| LIMIT 限制聚合输入 | D2 |

| 水位可超前于提交头部 | E5-ahead |
| 水位可回退 | E5-retreat |

### 两档都未排除（残余空间）

以下假设在两档材料中都碰巧正确，需要更多案例才能判别——这正是"展开所有交错会失去可读性"的边界：

- sum 的**负向**溢出（注入 int64 最小值；只演示了正方向）。
- 文本主键的同值并列收尾（两档的主键全是 int）。
- 多索引"候选最少"择优（扩展篇虽有两个 amplitude 索引，但没有制造候选数竞争的查询）。
- 输入预算边界：谓词 32 个、排序 8 项、limit 10000、128 活动事务、1000 键写集。
- 三事务以上交错、vacuum 与暂存写并发、索引构建与活动读者并发。
- changes 游标与 `history_base`、日志截断、检查点与备份摘要篡改（部分由 `examples/walkthrough.py` 的 14 条工作流覆盖，可与之互参）。

## "碰巧正确"的具体形态

以下设计点说明案例选择如何决定判别力——每条都是"少一个属性就放过一个错误假设"：

1. **种子里的三个 40**（样本 1、3、6）：没有重复排序键，B2 无法区分"并列恒按主键升序"与"并列随方向翻转"。
2. **种子里的两个 null**（样本 4、7）：没有 null，A1/A4/A5 全部失去判别力——`count(列)` 会与 `count(*)` 碰巧相等，sum 的空输入规则根本不可见。
3. **A5 用 `is_null`（全 null 输入）而不是空匹配集**：若错误规则是"sum 把 null 当 0"，全 null 输入下它得 0、正确规则得 null，可以分开；空匹配集（如 `sample > 100`）在两种规则下都得 null，判别不出。
4. **C1 的暂存 put 故意省略 amplitude**：若暂存行提供全部列，"整行替换"与"字段级合并"输出相同。
5. **X2 的 matched 巧合**：带事务（扫描）与不带事务（索引）的 matched 都是 3——单看计数会误判两条路径等价，必须看行内容（35 vs 30）与 `plan.access`。
6. **B3 的主键序等于插入序**：核心篇的已知盲点；扩展篇 X7b 在序号 11 才插入主键 7，把"按插入顺序"与"按类型化主键"分开。
7. **E2 同时测两个入口**：只测结构化入口无法排除"SQL 入口有自己的快照缓存/语义"；两个入口同一 410 报文才排除它。注意这里的论据是**快照选择发生在语义分叉之前**这一规则，而不是"两入口应当一致"本身。

## 代价对照（本次实测）

| 维度 | 核心篇 | 扩展篇 |
| --- | --- | --- |
| 检查数 | 42 | 30 |
| 实例与动作 | 1 个临时实例 | 2 个实例 + 备份/还原 + 1 次重启 |
| 探针运行时间 | 约 0.15 秒 | 约 0.35 秒 |
| 文档篇幅 | 约 280 行 | 约 170 行 |
| 引入概念 | 8 个（快照、暂存覆盖、null 匹配、排序与并列、聚合、提交、水位、410） | +6 个（索引候选、墓碑链、唯一检查时机、SQL 词法层、图像水位、重启持久） |
| 叙事结构 | 单一线性历史，可顺序通读 | 需同时跟踪目录（3 个索引）、墓碑链、两个实例的状态 |
| 与内核的耦合 | 只依赖公开语义规则；内核重构若不改语义，案例仍然成立 | X1/X2/X5 依赖执行事实（`plan.candidates`、`stats.keys/versions`）；内核改变内部表示而语义不变时，这些案例会失效 |

**扩展篇的边际收益递减是真实的**：它多排除 19 条假设，但每条新假设都需要引入新概念（索引内部、日志记录计数、图像格式），而这些概念本身又会催生新的错误假设（例如"候选数就是扫描数"）。交错空间随参与者数量指数增长，任何有限材料都只能是选择性的——扩展篇同样没有枚举三事务交错或容量边界。

**核心篇的盲区也是真实的**：没有索引就没有 X1/X2 的判别；没有乱序插入就没有 X7b；没有第二个实例就没有 X15。这些盲区在核心篇内不可见——读者无法从核心篇内部发现"有索引必走索引"从未被检验。

## 使用建议

- 目标是**学会推算查询答案**（null、排序、count/sum、快照与水位）：核心篇 足够，配合规则速查表即可覆盖日常推算。
- 目标是**解释执行事实**（plan 数字为何如此）、**评估升级影响**、**排查"两入口是否该一致"类疑问**：加读扩展篇对应主题，尤其是 X2（路径不影响结果）、X12（输入层的真实差异）、E2/X15（可算范围的边界）。
- 两档材料都是教学对照，不是正确性证明；独立期望模型与故障矩阵属于后续质量保障工作（见 `PROJECT_SPEC.md` 验证与测试边界）。

复现：`python3 examples/semantics_probe.py --group all`（全部 72 条检查，`ok=true`）。
